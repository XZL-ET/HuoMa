## 一、项目概述

### 1.1 产品定位

**火马**是一个企业微信活码管理平台（单租户版），为 XX 书店（省内大型连锁书店）生成并管理企微「联系我」活码。省内约 6,000 所学校一校一码，家长扫码添加书店企微员工后，系统自动完成客户分流、自动打标、信息收集、在职继承等全流程，支撑百万级家长的精细化运营。

### 1.2 业务规模

| 维度 | 规模 |
|------|------|
| 活码数量 | ~6,000 个（一校一码） |
| 客户总量 | 150 万 ~ 300 万 |
| 峰值场景 | 家长会期间 2 小时内集中扫码，回调峰值 400–1,000 条/秒 |
| 员工总数 | 12,000+ 接待员 + 服务老师 |

### 1.3 用户角色

| 角色 | 权限 | 使用者 |
|------|------|--------|
| 超级管理员 | 全部活码、全部员工、全部数据、系统配置 | 运营负责人 |
| 运营人员 | 指定区域/学校的活码管理 + 数据查看 | 各区域运营 |
| 企微员工 | 浏览/搜索活码、下载二维码、查看个人下载历史 | 书店企微员工 |
| 学校人员 | 自助查询本校活码、下载或联系负责人（无需登录） | 学校老师/工作人员 |

### 1.4 核心业务流程

```
运营创建活码（绑定接待员 + 服务老师 + 欢迎语 + 收集表单）
        │
        ▼
学校打印二维码，贴在家长会现场 / 发到家长群
        │
        ▼
家长扫码 → 企微服务端分配接待员 → 添加成功
        │
        ├─→ ① 企微回调 → Fast Ack → Redis Stream 异步消费
        │
        ├─→ ② 自动打标：平台标签 + 市/区/学校标签
        │
        ├─→ ③ 推送欢迎语 + 收集表单链接
        │         │
        │         ▼
        │    家长填写年级/班级 → 回调自动打标 + 企业微信备注
        │
        ├─→ ④ 日限计数 + 轮换检查（三级阈值预警）
        │
        └─→ ⑤ 在职继承：接待员 → 服务老师
                  │
                  ▼
             服务老师接管客户，发送交接欢迎语
```

## 二、功能模块

### 2.1 模块一：活码管理

#### 2.1.1 活码创建

| 功能 | 说明 |
|------|------|
| 手动创建 | 表单填写学校信息 → 调用企微 API 即时生成活码 |
| 批量导入创建 | Excel 上传（学校名/学校ID/市/区/场景/部门），异步创建，实时进度反馈 |
| 场景选择 | 支持「日常推送」（扫码率 ~10%）和「家长会」（扫码率 ~60%），自动计算接待员数量 |
| 部门绑定 | 活码绑定企微部门，扩容时优先同部门取人 |
| 多员工初始上码 | 支持逗号分隔多员工 initialAgentUserids + 自动从全局池补齐 |
| 自定义标签 | 活码创建时配置自定义标签，扫码自动打标 |
| 学校ID自动生成 | 批量导入时学校ID为空自动生成 |

**接待员分配公式**：
```
接待员数 = ceil(学生人数 × scene.scanRatio / agentDailyMax)
           clamp 到 [1, 100]
```

#### 2.1.2 活码列表与管理

| 功能 | 说明 |
|------|------|
| 分页列表 | 支持 20/50/100 条每页，聚合查询优化性能 |

| 排序 | 默认创建时间倒序，支持切换正序 |
| 活码详情 | 绑定的接待员/服务老师、今日/累计数据、轮换日志 |
| 活码编辑 | 修改学校信息、员工绑定、日限额、欢迎语、表单模板 |
| 活码状态管理 | active（正常）/ paused（暂停）/ full（满员）/ no_agent（无可用员工） |
| 轮换模式 | auto（自动）/ manual（人工审核），可按活码切换 |
| 列表导出 | 按当前筛选条件导出全量 Excel（POI SXSSFWorkbook 流式写入） |
| 批量操作 | 跨页全选、批量切换轮换模式、批量配置欢迎语/表单模板 |

#### 2.1.3 活码下载

| 功能 | 说明 |
|------|------|
| 单个下载 | 活码详情页下载二维码图片 |
| 批量下载 | 多选活码 → 打包 ZIP 下载（使用企微原始图片，不重新生成） |
| 员工下载中心 | 企微 OAuth 登录后浏览/搜索/下载活码，默认展示自己绑定的活码 |

#### 2.1.4 活码分组（教育联盟）

- 分组支持默认欢迎语和默认表单模板（活码未配置时继承分组设置）
- 活码列表左侧分组树导航

#### 2.1.5 配置继承链

### 2.2 模块二：全局员工池与轮换引擎

#### 2.2.1 全局员工池（GlobalAgentPool）

**核心理念**：所有接待员共享一个全局池，一人一记录，不再按活码维护独立后备池。

| 字段 | 说明 |
|------|------|
| `agent_userid` | 企微员工 UserID（UNIQUE） |
| `daily_max` | 日添加上限（默认 100–200） |
| `daily_current` | 今日已添加（Redis 实时同步） |
| `sort_order` | 分配优先级（数值越小越优先） |
| `department_id` | 所属企微主部门（用于同部门优先取人） |
| `status` | standby（待命）/ full（今日满员）/ blocked（管理员暂停） |

**状态流转**：
```
standby ──日限到达──→ full ──每日00:00重置──→ standby
standby ──管理员暂停──→ blocked ──管理员恢复──→ standby
```

#### 2.2.2 日限计数与轮换

**Redis 原子计数**（双 Key 策略）：
- `agent:daily:{userid}:{qrCodeId}` — 按码维度
- `agent:daily:total:{userid}` — 全局维度

**三级阈值机制**：

| 级别 | 默认阈值 | 动作 |
|------|----------|------|
| warn（预警） | 80% | 仅日志记录 |
| urgent（紧急） | 95%（家长会 70%） | 提前预激活后备员工（不标记当前员工满员） |
| full（日限） | 100% | 满员下码 + 从全局池取人扩容 + 企微 API 同步 |

**扩容取人优先级**：
```
① 同部门 standby → 按 sort_order 取
② 任意部门 standby → 按 sort_order 取（降级）
③ 全局枯竭 → 高危告警
```

**并发保护**：分布式锁 `rotate:lock:{qrCodeId}:expand`（Redis SETNX 10s TTL）

#### 2.2.3 手动回收接待员

- 活码详情页「回收闲置接待员」按钮
- 展示每个接待员的今日接待量，支持多选批量回收
- 回收逻辑：QrAgent.status → removed，GlobalAgentPool.status → standby
- 保护规则：服务老师不可回收、回收后至少保留 1 个 active 接待员

### 2.4 模块四：在职继承

#### 2.4.1 继承流程

```
客户扫码添加接待员 → 自动打标 → 在职继承
  ├─ 自动触发：InheritanceJob 每天 02:00 批量执行
  ├─ 手动触发：活码详情页 → 预览待转移数 → 确认执行（实时进度反馈）
  └─ TransferWorker 消费 TRANSFER_STREAM
       → 调用企微 API：transfer_customer
       → 每条间隔 200ms（防频率限制）
       → 记录 CustomerTransfer（pending_confirm）
```

#### 2.4.2 继承后处理

```
TransferMonitorWorker 每 10 分钟轮询 pending_confirm
  → 企微 API：get_transfer_result
    ├─ 成功 → 判断是否已填写收集表单
    │   ├─ 已填写 → 写继承备注 + 发送交接欢迎语
    │   └─ 未填写 → 发送提醒欢迎语（含收集表单链接）
    ├─ 拒绝 → 标记 rejected
    └─ 超时（>24h）→ 标记 timeout
```

#### 2.4.3 关键约束

| 企微约束 | 说明 | 平台应对 |
|----------|------|---------|
| 24h 等待期 | 微信客户需 24h 确认 | 列表标记「待确认」 |
| 90 天 1 次 | 同一客户 90 天只能被继承 1 次 | 分配前检查 |
| schoolId 隔离 | 继承时按 schoolId 过滤，防止跨活码客户转移 | 查询条件强制 schoolId |

### 2.5 模块五：员工管理与异常监控

#### 2.5.1 员工管理

- 员工列表：从企微 API 同步（`/user/simplelist`）
- 员工详情：跨活码全景视图（每个活码的日限/今日/余量/状态）
- 员工角色：统一为 receptionist（接待员）
- 员工同步：`EmployeeSyncService` 定期从企微同步，写入 `global_agent_pool.department_id`

#### 2.5.2 三层防封策略

**第一层：速率控制（实时，纯 Redis）**

| 窗口 | 阈值 | 动作 |
|------|------|------|
| 15 秒内 | >20 次 | 告警（日志 + 100ms 延迟） |
| 60 秒内 | >60 次 | 熔断：从所有活码移除，30 分钟冷却 |
| 24 小时内 | ≥3 次熔断 | 封锁：需管理员手动解封 |

**第二层：行为异常（巡检层，每 5 分钟）**

| 指标 | 阈值 | 等级 | 动作 |
|------|------|------|------|
| 添加通过率 | <30% | 中 | 标记异常，通知运营 |
| 被删率 | >10% | 中 | 标记异常，通知运营 |
| 全局池 standby=0 | — | 高 | 高危告警 |
| 全局池 standby<5 | — | 中 | 严重不足告警 |
| 单活码全员 >90% 负载 | — | 中 | 通知运营补充人手 |

**第三层：企微风控信号（回调层，实时）**

| 企微错误码 | 含义 | 动作 |
|-----------|------|------|
| 84061 | 操作频率过高 | 立即熔断 30 分钟 |
| 45009 | API 频率限制 | WAIT_AND_RETRY |
| 84073 | 已被对方删除 | 累计 >5 次 → 标记 |
| 25002 | 对方拒绝 | 累计 >10 次 → 标记 |

#### 2.5.3 每日重置（DailyResetWorker）

```
每日 00:00 执行：
① 清空 Redis agent:daily:* 键
② GlobalAgentPool: 所有 full → standby，daily_current 清零
③ QrAgent: 所有 full → active（排除 blocked/melted），同步到企微
④ 排除 blocked 员工：从 global_agent_pool 和 qr_agent 同时跳过
⑤ 生成昨日 DailyReport
```

### 2.7 模块七：消息异步发送

#### 2.7.1 欢迎语 + 表单发送

```
CallbackWorker.handleAddSuccess()
  └─ 新增：XADD → OUTBOUND_STREAM

  ├─ ① 解析欢迎语：活码 → 分组 → 系统默认（配置继承链）
```

#### 2.7.2 MessageGuard 服务

- 企微 `sendMessage` 每客户每天 1 条主动推送限制
- 48h 活跃窗口内可发送多条
- 两条消息间隔 300ms，防企微服务端队列丢弃
- 失败不重试，记录日志

## 三、技术架构

### 3.1 整体架构

```
                    ┌──────────────┐
    家长扫码 ──────→│  企微服务端   │ 企微扛分配
                    └──────┬───────┘
                           │ 回调 POST（400–1,000 QPS 峰值）
                    ┌──────▼───────┐
                    │    Nginx     │ 接收后秒回 200
                    │  (腾讯云ECS)  │
                    └──────┬───────┘
                           │
              ┌────────────▼────────────┐
              │      Spring Boot        │  一个 jar，多模块
              │                         │
              │  ┌───────────────────┐  │
              │  │ ① 回调接收层       │  │ → 验签+解密 → XADD Redis Stream
              │  │   秒回 200         │  │   不查库、不调 API
              │  ├───────────────────┤  │
              │  │ ② Worker 消费层   │  │ → 消费 Stream（Callback/Tag/
              │  │   异步批量处理     │  │   Outbound/Transfer Worker）
              │  ├───────────────────┤  │
              │  │ ③ 管理后台 API    │  │ → CRUD + @Scheduled 定时任务
              │  ├───────────────────┤  │
              │  │ ④ 学校自助查询    │  │ → 公开页面 /s，Caffeine 缓存
              │  ├───────────────────┤  │
              │  │ ⑤ 员工下载中心    │  │ → 企微 OAuth 登录
              │  └───────────────────┘  │
              │                         │
              │   Redis 7 + MySQL 8.0   │
              └─────────────────────────┘
```

### 3.2 削峰策略

| 层级 | 策略 | 说明 |
|------|------|------|
| Nginx | 收到回调立即 200 | 不解密、不查库、不阻塞 |
| Redis Stream | 消息队列削峰 | 自带 ACK + Consumer Group，不丢消息 |
| Worker | 批量消费 + 单线程 | 消除并发问题，每条间隔控制频率 |
| Redis 计数器 | `INCR` 原子操作 | 员工今日添加数，不查 DB |
| 定时落盘 | 每 5 分钟同步 | Redis 数据持久化到 MySQL |

### 4.2 设计原则

1. **无 JPA 关系注解**：所有实体使用显式外键 ID 字段（`Long qrCodeId`, `String agentUserid`），不使用 `@ManyToOne`/`@OneToMany`。避免懒加载陷阱，保持实体轻量，外键值与企微原生标识对齐。
2. **JSON 字段**：复杂结构（`form_template.fields`, `daily_report.detail_json`）使用 `columnDefinition = "JSON"` 存储。
3. **时间戳**：所有实体统一 `created_at`/`updated_at` + `@PrePersist`/`@PreUpdate` 自动维护。
4. **软删除**：`school` 表使用 `deleted` 标记，`qr_code` 使用 `status` 状态机。

## 十、开发规范

### 10.1 实体规范

1. 不使用 JPA 关系注解（`@ManyToOne`/`@OneToMany`），所有外键使用显式字段
2. JSON 字段使用 `@Column(columnDefinition = "JSON")` + String 类型存储
3. 所有实体统一 `createdAt`/`updatedAt` + `@PrePersist`/`@PreUpdate`
4. 使用 Lombok `@Data @Builder @NoArgsConstructor @AllArgsConstructor`

### 10.2 异步与事务

1. `@Async` 方法必须通过 Spring 代理调用，禁止 `this.` 自调用
2. 需要事务的异步方法使用 `@Lazy @Autowired private XxxService self` 自注入模式
3. 事务提交后回调使用 `TransactionSynchronizationManager.registerSynchronization()` 的 `afterCommit`

### 10.3 Worker 规范

1. 每个 Worker 处理一个 Redis Stream，使用 Consumer Group
2. 单线程 Worker 用 `XREAD`（阻塞读取），多线程用 `XREADGROUP`
3. 每条消息处理后 ACK，处理失败记录日志但不阻塞后续消息
4. 企微 API 调用间隔控制在 50ms–300ms，遇到 45009 走 WAIT_AND_RETRY

### 10.4 Redis Stream 使用

1. 创建 Consumer Group 前检查是否存在（`XGROUP CREATE ... MKSTREAM`）
2. 处理 PENDING 消息（重启后恢复未 ACK 的消息）
3. Stream Key 和 Group/Consumer 名称统一定义在 `RedisConfig`

### 10.5 日志规范

1. 使用 SLF4J + Lombok `@Slf4j`
2. Worker 入口/出口记录 debug 日志
3. 企微 API 调用记录请求摘要和响应状态
4. warn 级别用于需要关注但不影响主流程的异常
5. error 级别用于需要人工介入的异常
6. 避免在循环中打印 info 日志

### 10.6 Git 规范

- 主分支：`master`
- 功能分支：`feature/<功能名>`
- 修复分支：`fix/<问题描述>`
- Commit 格式：`<type>: <description>`（feat/fix/docs/refactor/perf/test）
- Co-Authored-By: Claude <noreply@anthropic.com>
