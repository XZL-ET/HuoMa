# 双机定时任务双跑 —— 影响面评估

- **日期**：2026-10-10
- **触发**：排查「服务器是否正常」时，从 `daily_report` 唯一键冲突顺藤摸瓜发现
- **状态**：已完成根因定位与影响面核实，**尚未改任何代码**
- **结论一句话**：生产是双节点 active-active，`@Scheduled` 定时任务大多没有分布式锁，两机同时跑同一任务。造成 1 处真实数据异常（消息提前进死信）、若干处重复告警/重复调用，**未发现数据丢失或业务状态错乱**。

### 两机都在实打实地处理业务流量（active-active，非主备）

2026-10-10 单日日志计数：

| 日志 | 节点 A (231) | 节点 B (232) |
|---|---|---|
| `OutboundMsgWorker` | 2,263 | 2,344 |
| `企微打标成功` | 572 | 464 |
| `已通过 send_welcome_msg 发送` | — | 941 |

两机消费同一组 Redis Stream（同一消费组、同一批消费者名），消息在两者之间分摊。
**所以这不只是「定时任务被跑了两遍」，业务 Worker 本身也是双活的**——这一点决定了修复方案不能靠
「把一台关掉」，必须给跨机共享的状态加锁。

## 四、对本次「服务器是否正常」结论的修正

- 基础设施（CPU / 内存 / 磁盘 / 服务状态 / Redis 积压 / 健康检查）**两台都正常**。
- 业务链路正常：10-10 15:01–15:04 两机均有大量打标成功与 `send_welcome_msg` 成功。
- 错误日志里的 `48002`（交接欢迎语）、`84061`、`40205` 均为**已知存量问题**，与本次双跑无关。
- 10-10 的 2 条死信（`msgId=1791613960062-0`、`1791615160057-0`）**无需人工补发**：DLQ 现为空（`XLEN=0`），两条已于 14:50 / 15:20 被自动重放，transfer stream `pending=0`。但它们之所以以 `retries=4` 提前进 DLQ，正是 3.1 首行那个翻倍机制造成的。
- `09:07:30` 五条 `PEL 回收扫描失败` 与双跑无关：是**停机竞态**，`LettuceConnectionFactory is STOPPING`，旧进程关闭时定时任务恰好触发（见附录）。

## 五、修复方向（已与用户确认：逐任务补 Redis 锁）

> **复核说明**：已排除「其实有全局锁只是我没找到」这一可能 —— 全仓库搜索
> `TaskScheduler` / `SchedulingConfigurer` / `@Aspect` / `Advisor` / `BeanPostProcessor`
> 无任何调度拦截实现；`application.yml` 的 `spring.task.scheduling.pool.size=4` 只调线程池大小，
> 是**每 JVM 独立**的；两机 `huoma.env` 逐字节一致，也无「主/备」开关。结论成立。

按仓库既有的 `setIfAbsent` 写法，为 3.1 / 3.2 的 8 个任务补锁，不引入新依赖。顺序按危害排序：

1. `PatrolWorker.recoverOrphanedPending` —— 唯一有真实数据伤害的
2. `DailyResetWorker.resetAndReport`
3. `PatrolWorker.patrol`（含其内部的 DLQ 自动重放；`lastDlqReplayTime` 需换成 Redis 键）
4. `PatrolWorker.dailyAnomalyAutoHeal`
5. `TransferMonitorWorker.checkDlq`
6. `StreamBacklogMonitor.checkAll`
7. `EmployeeSyncService.scheduledSync`
8. `InheritanceJob` 两个批次（低优先级，已有业务去重）

**每处改动的验证方式**：改完部署到两台后，次日 00:00 观察两机日志中
`===== 每日重置 + 日报生成开始 =====` 仅出现在一台；`daily_report` 自增 ID 跳号停止
（`(MAX(id)-MIN(id)+1) = COUNT(*)`）；03:07 的 `daily_anomaly_heal` 每天降为 1 条。

## 六、尚未核实

- `traffic_spike` 告警的同秒重复（94 组）是否由双跑造成，需逐条核对产生路径。
- 两机 Worker 是否使用**同名消费者**：已确认两机**都在消费同一批 Stream**（见第一节日志计数），
  但 Redis 里 `transfer-worker-1/2`、`outbound-worker-1..4` 等消费者名各自只出现一份，说明两机注册了
  **相同的消费者名**。XREADGROUP 的语义保证每组每条消息只投递给一个消费者，所以「新消息被处理两次」
  不会发生；真正的问题在 PEL —— 一个消费者名下的 pending 条目同时属于两个进程，
  谁是「孤儿」无法区分，这正是 `recoverOrphanedPending` 被两机各领一次的直接原因。
- 2026-09-20 ~ 09-29 期间两机每天 118~485 条 DLQ 入队（10-01 起降为 0）。该高峰疑似另一个已修复的独立问题（对应 `2026-09-29` 那次死信告警排查），本次未展开。
