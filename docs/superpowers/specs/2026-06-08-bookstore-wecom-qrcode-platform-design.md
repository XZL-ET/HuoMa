# XX书店 · 企业微信活码管理平台 产品设计文档

> 版本：v1.0 | 日期：2026-06-08 | 作者：产品设计

---

## 一、产品概述

### 1.1 产品定位

**企业微信活码管理平台（单租户版）**，为 XX 书店（省内大型连锁）生成并管理企微「联系我」活码。省内 ~6000 所学校一校一码，家长扫码添加书店企微员工后，系统自动分流、打标、收集信息并完成在职继承，支撑百万级家长精细化运营。

### 1.2 业务规模

| 维度 | 规模 |
|------|------|
| 活码数量 | ~6,000 个（一校一码） |
| 客户总量 | 150 万 ~ 300 万 |
| 峰值场景 | 家长会期间 2 小时内集中扫码，回调峰值 400-1000 条/秒 |
| 员工总数 | 12,000+ 接待员 + 服务老师 |

### 1.3 用户角色

| 角色 | 权限 | 使用者 |
|------|------|--------|
| 超级管理员 | 全部活码、全部员工、全部数据、系统配置 | 运营负责人 |
| 运营人员 | 指定区域/学校的活码管理 + 数据查看 | 各区域运营 |

### 1.4 核心业务流程

```
运营创建活码(绑定接待员+服务老师+欢迎语表单)
        │
        ▼
学校打印二维码，贴在家长会现场 / 发到家长群
        │
        ▼
家长扫码 → 企微服务端分配接待员 → 添加成功
        │
        ├─→ ① 回调：自动打标"书店平台/市/区/学校"
        │
        ├─→ ② 推送欢迎语（含收集表单）
        │         │
        │         ▼
        │    家长填写年级/班级 → 回调自动打标
        │
        └─→ ③ 触发在职继承
                  │
                  ▼
             客户转到该学校专属服务老师 → 服务老师接管
```

## 二、模块一：活码管理

### 2.1 功能清单

| 功能 | 说明 |
|------|------|
| 手动创建活码 | 表单填写学校信息 → 调用企微 API 即时生成 |
| 批量导入创建 | Excel 上传（学校名/学校ID/市/区），异步创建，进度可查看 |
| 活码列表 | 分页展示，支持地区/状态/学校名搜索筛选 |
| 活码详情 | 绑定的接待员/服务老师、今日/累计数据、轮换日志 |
| 活码下载 | 单个/批量下载二维码图片（300dpi 打印版 + 72dpi 线上版） |
| 活码外观自定义 | Logo（学校校徽）、主题色、引导文案、尺寸 |
| 员工绑定 | 值守接待员 + 后备池 + 继承目标服务老师 |
| 日限额 + 轮换 | 接待员日限到达自动从后备池补充 |
| 多级预警 | 80% 预警 / 95% 紧急 / 100% 触发轮换 |
| 轮换模式 | 全自动 / 人工审核，可按活码切换 |

### 2.2 活码自定义能力

| 可修改 | 不可修改 |
|--------|---------|
| 绑定/解绑接待员和服务老师 | state（学校ID，企微限制） |
| 每个接待员的日限 | 已打印出去的 URL |
| 活码外观（Logo/颜色/文案） | 二维码原始链接（除非换新码） |
| 活码暂停/启用 | — |
| 学校名称/地区/备注 | — |

## 三、模块二：客户管理与标签

### 3.1 标签体系

```
客户标签
├─ 系统自动标签（扫码即打，state 反查）
│   ├─ 平台标签：「XX书店家校服务」
│   ├─ 市标签：「A市」「B市」...
│   ├─ 区标签：「XX区」「YY区」...
│   └─ 学校标签：「XX第一小学」「XX实验小学」...
│
└─ 欢迎语收集标签（家长填表后自动打）
    ├─ 年级标签：「一年级」「二年级」...「高三」
    └─ 班级标签：「1班」「2班」...「20班」
```

### 3.2 打标时机

```
扫码添加成功
      │
      ▼
回调 state → 查学校表（市/区/学校名）
      │
      ▼
调用企微 API 打标：平台标签 + 市 + 区 + 学校
      │
      ▼
企微发欢迎语（含收集表单）
      │
      ▼
家长填写年级/班级 → 企微收集表单回调
      │
      ▼
自动打标：年级 + 班级
```

### 3.3 欢迎语配置

欢迎语在创建/编辑活码时设置，分为**扫码添加时欢迎语**和**继承后交接欢迎语**两部分：

```
活码欢迎语配置 (welcome_config) — 扫码添加时：

├─ text              欢迎语文案
│   "欢迎来到XX书店家校服务！添加福利官，领取专属购书优惠和免费学习资料。
│    📚 请先填写孩子信息，方便为您精准推荐～"
├─ collect_form       JSON  收集表单字段定义
│   [
│     {"name":"grade","label":"孩子年级","type":"select",
│      "options":["一年级","二年级",..."高三"]},
│     {"name":"class","label":"孩子班级","type":"select",
│      "options":["1班","2班",..."20班"]},
│     {"name":"child_name","label":"孩子姓名","type":"text","required":false}
│   ]
├─ form_callback_tag  bool   表单提交后是否自动打标（默认 true）
│
│ —— 以下为继承后交接欢迎语 ——
│
├─ transfer_filled_note        已填写客户的继承备注模板
│   "{{grade}}{{class}} | 孩子：{{child_name}} | 来源：{{school_name}}"
│
├─ transfer_filled_greeting    已填写客户的交接欢迎语
│   "{{parent_name}}您好～我是{{school_name}}的专属服务老师{{teacher_name}}，
│    以后孩子的学习资料和购书优惠都由我为您服务 📚"
│
├─ transfer_unfilled_greeting  未填写客户的提醒欢迎语
│   "{{parent_name}}您好～我是{{school_name}}的{{teacher_name}}！
│    为了给您精准推荐适合孩子的学习资料和优惠，
│    请先花30秒填写一下孩子信息哦 👇
│    📚 {{form_link}}"
│
└─ transfer_greeting_enabled   bool  是否启用继承后交接（默认开）
```

> 模板变量说明：`{{parent_name}}` 客户昵称、`{{school_name}}` 学校名、`{{teacher_name}}` 服务老师姓名、`{{grade}}` `{{class}}` `{{child_name}}` 从收集表单取值、`{{form_link}}` 系统自动生成收集表单链接。发送时实时替换。

### 4.4 三层防封策略

#### 第一层：速率控制（代码层，实时）

```
Redis 滑窗计数（15秒窗口）
  │
  ├─ 15秒内添加 > 20人 → ⚠️ 降速（暂缓5秒再分配）
  └─ 1分钟内添加 > 60人 → 🔴 熔断（立即暂停，防止触发企微风控）
```

#### 第二层：行为异常（巡检层，每5分钟）

| 指标 | 阈值 | 等级 | 动作 |
|------|------|------|------|
| 添加通过率 | < 30% | 中 | 标记异常，通知运营 |
| 被删率 | > 10% | 中 | 标记异常，通知运营 |
| 连续添加失败 | 5次同原因 | 高 | 暂停该员工 |
| 单活码全员高负载 | 全部>90% | 中 | 通知运营补充人手 |

#### 第三层：企微风控信号（回调层，实时）

| 企微错误码 | 含义 | 动作 |
|-----------|------|------|
| 84061 | 操作频率过高 | 🔴 立即熔断30分钟 |
| 84073 | 已被对方删除 | 累计>5次 → 标记 |
| 25002 | 对方拒绝 | 累计>10次 → 标记 |
| 20302 | 对方已添加 | 正常，不算异常 |
| 其他未知异常码 | — | 人工跟进 |

### 4.5 熔断与恢复

```
触发熔断
    │
    ▼
从所有活码移除 → 记录异常 → 通知运营
    │
    ▼
30分钟后自动检测
    │
  ┌─┴──────────┐
  │ 恢复正常     │ 异常仍存在
  │ 加回活码     │ 继续观察
  └────────────┘
  同一员工24h内熔断3次 → 人工处理，不再自动恢复
```

### 4.6 日限额与每日重置

```
接待员日限额管控：
├─ 每个活码独立设日限（如 200/天）
├─ 所有活码日限总和 ≤ 员工日总上限
├─ 今日已加数 = Redis INCR（实时）
├─ 达日限 → 从该活码移除 → 按轮换模式处理
└─ 每日 00:00 → 全部清零 → 自动加回（被封/暂停的除外）

服务老师接手管控：
├─ 服务老师日接上限（从继承接收的数量）
├─ 达上限 → 转给后备服务老师
└─ 每日 00:00 重置
```

## 七、技术架构

### 7.1 整体架构

```
                    ┌──────────────┐
    家长扫码 ──────→│  企微服务端   │ 企微扛分配
                    └──────┬───────┘
                           │ 回调 POST（400-1000 QPS 峰值）
                    ┌──────▼───────┐
                    │    Nginx     │ 接收后秒回 200
                    │  (腾讯云ECS)  │
                    └──────┬───────┘
                           │
              ┌────────────▼────────────┐
              │      Spring Boot        │  一个 jar，三个模块
              │                         │
              │  ┌───────────────────┐  │
              │  │ ① 回调接收层       │  │ → 校验签名 → 写 Redis Stream
              │  │   秒回 200         │  │   不查库、不阻塞
              │  ├───────────────────┤  │
              │  │ ② Worker 消费层   │  │ → 消费 Redis Stream
              │  │   批量处理         │  │   入库 + 打标 + 继承 + 计数
              │  ├───────────────────┤  │
              │  │ ③ 管理后台 API    │  │ → 活码/员工/客户 CRUD
              │  │   + 定时巡检      │  │   @Scheduled 巡检 + 重置
              │  └───────────────────┘  │
              │                         │
              │   Redis + MySQL         │
              └─────────────────────────┘
```

### 7.2 削峰策略

| 层级 | 策略 | 说明 |
|------|------|------|
| Nginx | 收到回调立即 200 | 不解密、不查库、不阻塞 |
| Redis Stream | 消息队列削峰 | 自带 ACK + Consumer Group，不丢消息 |
| Worker | 批量消费 + 批量写 DB | 多条回调合并 INSERT，减少 DB 连接 |
| Redis 计数器 | `INCR` 原子操作 | 员工今日添加数，不查 DB |
| 定时落盘 | 每 5 分钟同步到 MySQL | Redis 数据持久化，不怕重启 |

### 7.3 部署方案

```
1 台腾讯云 ECS（现有 2C 7.5G 100G）
├─ Nginx（Docker）
├─ Spring Boot jar（直接运行，非 Docker）
├─ Redis 7（Docker 或直接装，2G max memory）
└─ MySQL 8.0（保留在阿里云那台，或迁过来）

备用：阿里云 2C 3.4G（现有）
└─ MySQL 8.0 → 过渡使用，后续建议换成 RDS
```

### 7.4 技术栈

| 层 | 选型 | 原因 |
|----|------|------|
| 语言 | Java 17 + Spring Boot 3.x | 你已有的技术栈 |
| Web | Spring MVC + Undertow | 轻量，并发性能好 |
| DB | MySQL 8.0 | 已有 |
| 缓存/队列 | Redis 7（Stream + Hash + String） | 一个 Redis 同时做队列、计数、缓存 |
| 前端 | Thymeleaf + HTMX + Bootstrap 5 | 你一个人搞，SSR 最简单 |
| 定时任务 | Spring @Scheduled | 巡检 + 日报生成，无需额外调度器 |
| 企微 SDK | wecom-sdk（开源）或直接 HTTP 调用 | 轻，无官方重量级 SDK |

### 7.5 为什么不用

| 不用的 | 原因 |
|--------|------|
| RocketMQ / Kafka | Redis Stream 够用，少一个中间件、少一个故障点 |
| 微服务 / K8s | 你一个人，单体启动更快、排查更简单 |
| Vue/React SPA | SSR 零配置，不需要前后端分离的部署复杂度 |
| Docker 部署 Spring Boot | 直接 java -jar 跑，出问题看日志直接 |
| 云数据库 RDS | 先用现有 MySQL，后续数据和钱够了再迁 |
